## 1. Core Philosophy & Responsibility Mandate

`Learning` answers the fundamental cognitive question: *Given what happened across past episodes, what should change so future episodes perform better?*

To preserve the IDUN V3 constitutional invariants (`Layer 1 Version 1.0.0-FROZEN`), `Learning` answers this question by **proposing, never by acting**. Everything `Learning` synthesizes is an immutable candidate snapshot until a separate, non-cognitive gate and rollout engine admit it.

### Responsibility Boundaries
* **Owns:** Windowed experience aggregation, candidate strategy snapshot synthesis (via open `LearnerRegistry`), offline candidate validation (`Draft` $\rightarrow$ `Validated`), and versioned publishing to the `SnapshotRegistry`.
* **Explicitly Does Not Own:** Memory storage/eviction (`Memory`), active strategy activation (`SnapshotRegistry.get_active`), live deployment/canary traffic control (`Rollout Executor`), constitutional threshold mutation (`Executive`), or real-time cognitive reasoning/decision-making.

## 2. Asynchronous Lifecycle & State Machine

Unlike `Understanding`, `Reasoning`, `Planning`, and `Decision`, `Learning` is **not episode-synchronous**—it never executes on the critical path of a live turn. It runs asynchronously on windowed historical corpora (`O(N)` window size).

## 3. Production Hardening & Architectural Invariants

### A. Executive-Only Ownership of `LearningPolicyProfile`
`Learning` consumes a read-only, versioned `LearningPolicyProfile` (`learning_rate`, `min_sample_size`, `validation_thresholds`, `drift_thresholds`, `domain_weights`). Only `Executive` (or external deployment governance) may publish a new active `LearningPolicyProfile`. `Learning` never tunes the rules that govern its own validation gates.

### B. Write-Only `LearningTrace`
`Learning` emits diagnostic traces (`LearningTrace`) strictly to `Memory` for `Reflection` to evaluate post-hoc. `Learning` itself **never queries or consumes historical `LearningTrace` objects during candidate generation**, preventing recursive memory accumulation.

### C. Partitioned `ReflectionReport` Ingestion (Zero Self-Reference)
`ReflectionReport` schemas are strictly partitioned into two categories:
```go
type ReflectionReport struct {
    ReportID             string               `json:"report_id"`
    Category             ReportCategory       `json:"category"` // COGNITIVE_PERFORMANCE vs LEARNING_DIAGNOSTICS
    CognitivePerformance *CognitivePerformance `json:"cognitive_performance,omitempty"`
    LearningDiagnostics  *LearningDiagnostics  `json:"learning_diagnostics,omitempty"`
}
```
* **Ingestion Filter Rule:** `Learning`'s `Aggregation` stage strictly filters `WHERE category == 'COGNITIVE_PERFORMANCE'`.
* **Diagnostic Isolation:** `LEARNING_DIAGNOSTICS` (evaluating learner contribution, validation quality, and rollout metrics) is **strictly barred from `Learning` ingestion**. It is consumed exclusively by `Executive` (or `Governance`).

### D. System Health / Governance Bridge (`GovernanceBridge`)
To prevent `Executive` from drifting into a low-level statistical system auditor while awaiting a dedicated Layer 2 `System Health / Governance` subsystem:
1. `ReflectionReport.LearningDiagnostics` flows through a bounded `GovernanceBridge` adapter inside `Executive` (or `infrastructure/governance`).
2. The bridge translates raw statistical metrics into crisp `HealthRecommendation` imperatives (`RECOMMEND_PAUSE_ROLLOUT`, `RECOMMEND_TRIGGER_ROLLBACK`, `RECOMMEND_DISABLE_LEARNER`, `RECOMMEND_HUMAN_REVIEW`).
3. `Executive` core consumes solely `HealthRecommendation` enums. When Layer 2 Governance is deployed, the bridge detaches cleanly with zero core API changes.

### E. Explicit Fail-Fast Termination (`CAPABILITY_UNAVAILABLE`)
If a `Learner` or `LearningPolicyProfile` requests a computational capability (`SupportsReinforcementLearning`, `SupportsOnlineLearning`, `SupportsQuantumSimulation`) where `deployment_manifest.has_capability == false`, `Learning` aborts immediately:
$$\text{ResultStatus} = \text{ABSTAINED}, \quad \text{TerminationReason} = \text{CAPABILITY\_UNAVAILABLE}$$

## 4. Signature-Based Learner Registry (`LearnerRegistry`)

To ensure 30-year extensibility across new domains (`Robotics`, `Vision`, `Social`, `Quantum`) without modifying `Learning` orchestration code, learners register via schema signatures rather than hardcoded subsystem identifiers:

## 5. Bifurcated Validation & Structural Safety

### Parameter Optimization vs. New Strategy Proposals
```
[Candidate Snapshot Generated]
               │
               ├── if Parameter Optimization ──► [Ordinary Validation Gate: Statistical + Constitutional Checks]
               │
               └── if New Strategy Proposal  ──► [Structural Validation Stage]
                                                        ├── Static Syntax & Schema Verification
                                                        ├── Big-O Complexity & Execution Timeout Proof (<= max_ms)
                                                        ├── Memory Footprint Bounds Proof (<= max_mb)
                                                        ├── Cycle / Deadlock / Infinite Loop Detection
                                                        └── Public API Adherence Verification
                                                                  │
                                                                  ▼
                                                   [Validated -> Shadow -> Canary -> Active]
```

### Generalized Artifact Rule
*"Learning may generate only artifacts whose schemas are already supported by frozen runtime engines."*  
`Learning` never expands runtime semantics or generates arbitrary Turing-complete code. It strictly populates declarative data structures (`Composite Strategy Graphs`, `Prompt Templates`, `Behavior Trees`, `Parameter Weights`) that receiving engines possess pre-verified static interpreters to execute safely.

## Pre-Phase 2 Refinements & Architecture Invariants

Prior to Phase 2 engine implementation, the `2.0.0-FROZEN` specification incorporates four non-breaking architectural refinements to guarantee exact boundary isolation and multi-decade replayability:

### 1. AggregationPolicy (`types.go`, `config.go`)
An immutable domain profile (`AggregationPolicy`) owned strictly by Executive and consumed passively by `Learning`. It governs:
* `Strategy`: Default aggregation strategy selector (`COGNITIVE_PERFORMANCE_DEFAULT`).
* `SamplingMethod`: Deterministic vs. Uniform vs. Stratified (`SamplingMethod`).
* `OrderingStrategy`: Deterministic chronological ascending vs. domain priority (`OrderingStrategy`).
* `MergePolicy`: Deduplication and retention rules (`MergePolicy`).
* `WindowDuration`, `MaximumArtifacts`, `MaximumMemoryBytes`, and `DomainPriorities`.
* **Boundary Proof**: `Learning` never self-selects sampling windows or modifies policy parameters; Executive retains sole publication and governance authority.

### 2. ValidationEvidence (`types.go`)
Every `ValidationResult` embeds factual, purely observational counters (`ValidationEvidence`):
* `SampleCount`, `DriftScore`, `ReplayVerified`, and exact check counts (`StructuralChecks`, `ConstitutionalChecks`, `StatisticalChecks`, `ConstraintChecks`).
* **Boundary Proof**: Evidence contains zero causal interpretation or subjective judgment. `Reflection` consumes these objective metrics post-hoc without rerunning the validation pipeline.

### 3. LearnerVersion (`interfaces.go`)
The `Learner` interface exposes both `LearnerID() string` and `LearnerVersion() string` (`e.g., "1.0.0"`).
* **Boundary Proof**: Lineage tracking and snapshot replay record exact semantic versions (`ReasoningLearner v1.0.0` vs `v2.0.0`), enabling bit-identical historical reconstruction across decades without altering algorithm execution semantics.

### 4. Future SkillPackage Support (Architecture Note)
To preserve strict separation between **Knowledge Acquisition** (which creates novel capabilities and curricula) and **Learning** (which improves existing capabilities from experience):
* `Learning` may improve supported static structures or parameter weights through empirical experience.
* `Learning` MUST NOT create or synthesize new `SkillPackage` artifacts.
* A future **Knowledge / Skill Acquisition** subsystem will own curriculum-based teaching and initial `SkillPackage` creation.
* Once a `SkillPackage` is created and supported, `Learning` treats it exactly like any other supported artifact, optimizing and refining it passively without violating separation of concerns.

## Pre-Phase 3 & Pre-Phase 4 Refinements (`2.0.0-FROZEN`)

### 5. CandidateLineage & Provenance Chain (`types.go`)
Every candidate records its long-term evolutionary history (`CandidateLineage`) alongside immediate `ReplayMetadata`:
* `ParentSnapshot`: Immediate parent snapshot ID (`CandidateSnapshot.SnapshotID`).
* `AncestorSnapshot`: Root origin snapshot ID (`v1.0.0` or earliest ancestor).
* `GenerationDepth`: Depth of evolutionary generations (`uint32`).
* **Boundary Proof**: Lineage is purely metadata for observability, evolutionary tracking, and deterministic replay; `Learning` never uses generation depth for subjective self-evaluation.

### 6. LearningCampaign & CampaignSummary (`types.go`)
To improve multi-cycle observability and cross-module reporting without memory bloat:
* `LearningCampaign`: Groups related learning cycles under a single objective (`CampaignID`, `Objective`, `StartTime`, `EndTime`, `CampaignStatus`) scheduled strictly by `Executive`. Learning records metadata and increments mechanical counters (`LearningCycles`, `CandidatesGenerated`, `CandidatesValidated`, `ExperimentsCreated`, `SnapshotsPublished`); `Learning` never evaluates campaign success or makes policy activation decisions.
* `LearningCampaignSummary`: Compact $O(1)$ telemetry aggregate (`TotalCycles`, `TotalCandidates`, `AverageValidationConfidence`, `AverageExecutionTimeUs`, `AverageReplayFidelity`, `CampaignDuration`) designed specifically for `Reflection` (`idun/intelligence/reflection`) and long-term trend analysis.

### 7. Statistical Telemetry & Preference Ranking (`trace_stats.go`, `ranking.go`, `experiment.go`)
Phase 4 completes the orchestration, ranking, and telemetry infrastructure while maintaining strict read-only / write-only responsibility boundaries:
* `TraceStatisticalSummary`: Bounded $O(1)$ statistical telemetry (`TotalArtifactsAnalyzed`, `MeanValidationScore`, `MinValidationScore`, `MaxValidationScore`, `EstimatedDriftScore`, `ReplayFidelityRatio`, `DomainCoverageRatio`) embedded inside `LearningTrace`. It enables `Reflection` to analyze cycle health and drift trends without unbounded memory accumulation.
* `CandidateRankingEngine`: Deterministic ordering (`RankCandidates`) prior to validation gate processing, prioritizing high-impact domain strategy proposals and stable generation depths while preserving exact reproducibility.
* `ListActiveExperimentsPrioritized`: Bounded experiment retrieval ordered by descending `Priority` and evaluation ratios, ensuring high-priority shadow and canary evaluations receive scheduling precedence.
* `NewDefaultLearnerRegistry()`: Thread-safe built-in registry out of the box with all 9 domain, statistical optimization, and cross-domain synthesis learners.
