# Phase 4B.6 Readiness Audit: Compound Intent Detection

This document specifies the architectural design and readiness requirements for Phase 4B.6 (Compound Intent Detection) within the IDUN V3 cognitive pipeline.

## 1. Goal Definition

In the Understanding layer, a **Goal** is the foundational unit of user intent combined with its associated context. It is the fully resolved semantic instruction that the cognitive pipeline acts upon.

*   **Intent**: The classified objective or action type (e.g., `query_weather`, `manage_reminders`).
*   **Goal**: The instantiation of an intent, bundled with its specific extracted slots, semantic objects, and temporal anchors (e.g., `query_weather` + `location: Seattle`). 
*   **Capability**: The systemic tool or application that mechanically executes the Goal (e.g., `app-weather-1`).
*   **Execution Plan**: The DAG (Directed Acyclic Graph) generated by the Planning layer that determines the orchestration, dependencies, and execution sequence of the Capabilities.

## 2. Compound Intent Definition

A **Compound Intent** is a single user utterance that contains multiple distinct, independent goals joined by coordinating conjunctions or sequential markers. 

**Positive Example:**
*   `Open Chrome and search for OpenAI.`
    *   **Goal 1**: Open Chrome (Intent: `open_application`, Slot: `Chrome`)
    *   **Goal 2**: Search OpenAI (Intent: `search_web`, Slot: `OpenAI`)

**Negative Example (Not a Compound Intent):**
*   `Open Chrome with administrator privileges.`
    *   **Single Goal**: Open Chrome (Intent: `open_application`, Slot: `Chrome`, Modifier: `administrator privileges`)
    *   *Reason*: The modifier describes *how* to execute the single goal; it is not a distinct second goal.

## 3. Supported Connectors

The deterministic Understanding layer must split utterances based on specific conjunctions. 

| Connector | Status | Justification |
| :--- | :--- | :--- |
| `and` | **Supported in 4B.6** | Standard coordinating conjunction; creates distinct independent goals. |
| `then` | **Supported in 4B.6** | Standard sequential conjunction; implies strict ordering of distinct goals. |
| `after that` | **Supported in 4B.6** | Standard sequential conjunction. |
| `also` | **Supported in 4B.6** | Standard coordinating conjunction. |
| `as well as` | **Supported in 4B.6** | Standard coordinating conjunction. |
| `before` | **Deferred** | Requires dependency inversion and temporal reordering within Understanding. Complex for deterministic grammar splitting. |
| `after` | **Deferred** | Same as `before`. |
| `while` | **Deferred** | Requires asynchronous/parallel capability execution orchestration, which belongs in Planning, not simple deterministic Understanding. |

## 4. Nested Connectors

**Status**: **Limited (Flat Sequential Only)**

*   **Supported**: Flat linear sequences (e.g., `Open Chrome and then search Google and then open Gmail.`)
*   **Supported**: Linear multi-actions (e.g., `Create a reminder and take a note and send a message.`)
*   **Deferred**: Complex hierarchical nesting requiring Abstract Syntax Tree (AST) evaluation (e.g., `Open Chrome and (if it fails, open Firefox) or search Google.`)

Phase 4B.6 will only implement flat, sequential splitting of the input into an ordered list of goals.

## 5. Output Contract

Currently, the frozen Cognitive API Specification dictates that the Understanding layer produces a `SemanticInterpretation` (with a single Intent, Slots, etc.). 

**Preferred Structure:**
To accommodate compound intents while strictly preserving the frozen `SemanticInterpretation` contract, the Understanding layer will output a new wrapper object, `UnderstandingBatch`.

```json
{
  "UnderstandingBatch": {
    "Interpretations": [
      {
        "SemanticInterpretation": {
          "Intent": "open_application",
          "Slots": {"app": "Chrome"}
        }
      },
      {
        "SemanticInterpretation": {
          "Intent": "search_web",
          "Slots": {"query": "OpenAI"}
        }
      }
    ]
  }
}
```

*Why:* By introducing `UnderstandingBatch` (which contains an ordered collection of existing `SemanticInterpretation` objects), we preserve the frozen Cognitive API. This avoids contract drift, keeps downstream components completely backward compatible, and allows single-intent and compound-intent processing to safely coexist without redesigning core structures.

## 6. Understanding Boundary

To preserve IDUN V3's strict separation of concerns, the **Understanding** layer strictly bounds what it can and cannot do during Phase 4B.6.

**Understanding MUST:**
*   Detect multiple goals from a single utterance.
*   Split the user input deterministically.
*   Preserve the literal ordering of the goals as spoken.
*   Preserve slots, semantic objects, and temporal objects per goal.

**Understanding MUST NOT:**
*   Optimize execution.
*   Reorder goals based on efficiency or temporal logic.
*   Build execution dependencies between goals.
*   Infer workflows or missing intermediate steps.
*   Perform reasoning or planning.
*   Execute capabilities.

## 7. Planning Compatibility

The Planning layer consumes the output from Understanding (via Reasoning). 
*   **Expected Interaction**: Planning (and other downstream components like Reasoning, Decision, Presentation) will consume the new wrapper (e.g., `UnderstandingBatch` / `ReasoningBatch`) by iterating over its contained `SemanticInterpretation` objects.
*   **Plan Generation**: For each `SemanticInterpretation`, Planning discovers the appropriate Capability and generates a corresponding Plan Node. 
*   **Sequence**: Because Understanding preserves literal ordering in the batch, Planning will construct the Directed Acyclic Graph (DAG) by making Node 2 dependent on Node 1, Node 3 dependent on Node 2, etc. (Strict linear orchestration).

## 8. Verification Corpus

### Positive Cases (Compound Goals)
1.  **`Open Chrome and search Google.`**
    *   *Classification*: Compound Goal. Two distinct systemic capabilities (`open_app`, `search`).
2.  **`Create a reminder and take a note.`**
    *   *Classification*: Compound Goal. Two distinct domains (`reminders`, `notes`).
3.  **`Check the weather then remind me to take an umbrella.`**
    *   *Classification*: Compound Goal. Sequential distinct capabilities (`weather`, `reminders`).
4.  **`Open VS Code then open my project.`**
    *   *Classification*: Compound Goal. Sequential operations.
5.  **`Delete report.pdf and empty the recycle bin.`**
    *   *Classification*: Compound Goal. Two distinct file operations.

### Negative Cases (Single Goals)
1.  **`Open Chrome with administrator privileges.`**
    *   *Classification*: Single Goal. `administrator privileges` is a slot modifier, not a distinct capability.
2.  **`Delete report.pdf from Downloads.`**
    *   *Classification*: Single Goal. `from Downloads` acts as a location parameter slot for the deletion capability.
3.  **`Restart the computer tomorrow.`**
    *   *Classification*: Single Goal. `tomorrow` is a Temporal Anchor attached to the restart goal.
4.  **`Open Chrome using my work profile.`**
    *   *Classification*: Single Goal. `work profile` is an entity slot modifier.

## 9. Success Criteria

Phase 4B.6 will be considered complete when:
1.  Every distinct goal within a supported compound utterance is independently recognized.
2.  The literal chronological ordering of the goals is preserved.
3.  Raw slots are accurately distributed to their respective goals without mutation.
4.  Semantic objects remain unchanged.
5.  Temporal objects remain unchanged.
6.  No reasoning, planning, or execution logic leaks into the Understanding boundary.
7.  No regressions occur in the existing manual interaction suites or unit tests.

## 10. Freeze Recommendation

*   **Is the current Cognitive API sufficient for compound intents?**
    Yes, the `SemanticInterpretation` contract itself is fully sufficient and must not be modified.
*   **Is any schema change required?**
    Yes, but exclusively to introduce the new `UnderstandingBatch` and `ReasoningBatch` wrapper schemas. The underlying schemas remain untouched.
*   **Is any semantic contract change required?**
    No changes are required for existing contracts. We are simply introducing a batch wrapper that aggregates them.
*   **Is Phase 4B.6 ready for implementation?**
    Yes.
*   **What are the architectural risks?**
    The primary risk is ambiguous slot assignment (e.g., determining which distinct `SemanticInterpretation` an isolated temporal anchor or target object belongs to when multiple goals are present). 
*   **What should be verified before freezing Phase 4B.6?**
    We must verify that downstream layers (Planning, Reasoning, Decision, Presentation) are successfully updated to iterate over the `UnderstandingBatch` / `ReasoningBatch` without breaking their existing logic for singular `SemanticInterpretation` evaluation.

## 11. UnderstandingBatch Invariants

*   Every UnderstandingBatch contains one or more SemanticInterpretation objects.
*   Every contained SemanticInterpretation must be a valid standalone interpretation.
*   Goal order must always match the user's spoken order.
*   Understanding must never reorder goals.
*   Goals are immutable after creation.

## 12. Single-Goal Compatibility Rule

*   Even a single user intent returns an UnderstandingBatch.
*   A single-intent request produces a batch containing exactly one SemanticInterpretation.
*   There is no separate return type for single-intent requests.
*   Downstream components always consume the same wrapper.

## 13. Future Metadata Extension

The UnderstandingBatch wrapper is strictly reserved as an extension point for future metadata without modifying the core SemanticInterpretation schema.

*Possible future metadata includes:*
*   Parser Version
*   Processing Metrics
*   Diagnostics
*   Trace Metadata
*   Parsing Confidence
*   Timing Information

*(Note: These fields are not implemented in Phase 4B.6. The wrapper is merely reserved as the future extension point).*

## 14. Architecture Freeze Declaration

**The Phase 4B.6 architecture is now frozen.**

Future implementation must preserve the existing SemanticInterpretation contract and extend the Understanding layer exclusively through the UnderstandingBatch wrapper.
